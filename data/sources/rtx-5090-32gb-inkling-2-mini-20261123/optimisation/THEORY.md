# Inkling 2 Mini: measured hardware and conditional ceilings

Generated by `python3 theory.py` using only checkpoint headers/config and `hardware.json`. No GPU work is performed by this script.

Weights revision: `ed40e7da625f594fc9c4990f5f66be24873c22d7`. All bytes below are decimal GB unless marked GiB.

## Model accounting

The checkpoint has 24 physical text layers. Core layers 6–17 run three times, giving 48 layer visits per token: 8 full-attention and 40 local-attention visits. The three-layer draft has one full-attention layer and two local layers.

| Component | Physical GB | Visit-weighted GB per target forward |
|---|---:|---:|
| Routed experts, including FP4/FP8 payload and scales | 15.670 | 29.430 before routing |
| Other layer weights | 1.365 | 2.787 |
| Output head | 0.926 | 0.926 |
| Input embedding | 0.926 | Row lookup: 4608 bytes |
| Vision | 0.637 | Excluded for text decode |
| Draft checkpoint | 0.636 | Once per block, as a traffic scenario |

The input embedding and output head have distinct checkpoint offsets. This proves separate stored tensors, not whether the runtime aliases parameters or their numerical values happen to match. The baseline draft uses the target output projection. Its BF16 head scan adds about 0.926 GB per draft block, but not another0.926GB of unique checkpoint weights. Some MTP tensors are lookup tables or recurrent Markov projections. The one-scan estimate needs kernel profiling: locality can lower traffic, whereas recurrence and reloads can raise it.

Expert payload and scale bytes are counted from safetensors offsets, not parameter count×bits. Physical layers 0–19 use packed FP4 weights; layers 20–23 use FP8 weights (F8_E4M3 in the checkpoint). Effective active matrix parameters, excluding final head, are 1.305B dense plus 3.058B routed. This is 8.725GFLOP/token before attention and other operations.

## KV and memory

BF16 full KV: 36,864B/token total (32,768 target + 4,096 draft). At 131072 tokens this is 4.50GiB. The allocated 4096-token SWA pool adds 0.656GiB. The actual sliding window is 1024 tokens, so each step needs only that window logically. State caches, allocator metadata, graph buffers, temporary activations and driver memory are additional.

The server log independently reports target full K/V 2.00 GiB each and draft full K/V 0.25 GiB each, agreeing with this accounting. It also reports approximately 0.02 GiB conv-state and 0.04 GiB intermediate conv-window storage for eight state slots. Checkpoint size alone is therefore not a memory-fit estimate.

## Hardware measurements

- Device copy: **1529GB/s**, median of ten rounds, each copying a 1 GiB buffer 50 times; read+write bytes counted.
- BF16 dense GEMM: **219.8TFLOP/s** at 4096³ and **230.8TFLOP/s** at 8192³ (ten rounds each).
- FP8 dense GEMM: **542.7TFLOP/s** at 4096³, median of six rounds.

## Decode bandwidth scenarios

These are optimistic bandwidth-only scenario estimates, not measured performance limits or an achievable performance promise. They assume the full attention KV is read once per block, good query-row reuse, one draft-block forward, and no whole-core weight retention across loop passes.

`target_step = dense_visits + target_head + expert_visits × expert_union + target_KV`

`draft_step = MTP_payload + shared_head_read + draft_KV`

`tokens/s = measured_bandwidth × accepted_tokens_per_step / (target_step + draft_step)`

DSpark proposes a block in parallel. Multiplying the entire draft transformer/head by seven serial draft passes would substantially overstate its traffic. Eight verification rows may select the same experts or different experts; the scenarios use perfect overlap (top 8/128) and independent routing [1−(1−8/128)^8]. Actual routing, reloads, dequantization and cache reuse must be profiled.

|---|---:|---:|---:|
| 8,192 | 255 | 260 | 604 |

| 114,688 | 161 | 213 | 398 |
| 131,072 | 153 | 207 | 378 |

The JSON also includes acceptance 2, 4, 6 scenarios. Compare a clean non-looping measured panel only with the scenario matching its measured acceptance. Do not divide a looping-output token rate by this table or call the result hardware efficiency. No percentage of a single practical ceiling is justified until routing/acceptance and per-step traffic are profiled.

## Prefill, TTFT and startup limitations

A defensible mixed-precision prefill ceiling is **not yet measured**. BF16/FP8 dense GEMM cannot stand in for the mixed NVFP4/FP8 grouped-MoE kernels. The expert path has different precision, small per-expert row counts, routing and dequantization overhead. Applying a blanket 50% BF16 peak to the whole model would give a misleading number. Report prefill as measured prompt tokens/TTFT, and profile stages or measure the actual MoE path before assigning a ceiling.

Short TTFT includes tokenization, scheduling and a target forward; the bandwidth scenarios are only a weight/KV floor, not an end-to-end TTFT prediction. A startup floor additionally needs measured checkpoint read speed and allocation/JIT time, which this script does not measure. Persistent caches are a separately testable startup lever.

## Remaining uncertainty

- Core layer weights are revisited for each of three passes; no whole-core L2 retention is assumed.
- Target input embedding is a row lookup, not a scan of the complete embedding table.
- Input embedding and output head have separate checkpoint storage; the headers alone do not prove numerical equality or runtime parameter aliasing.
- Draft projection reuses the target output head in the baseline runtime; it is read once per block in this model, not seven serial times.
- The complete 635 MB MTP payload is included once per block as a scenario; lookup locality can lower traffic, while Markov recurrence and reloads can raise it.
- Expert overlap and independent routing are scenarios, not guaranteed lower/upper bounds on observed DRAM traffic.
- Full KV is read once per verification block and once by draft attention; kernels may reload it per tile, increasing traffic.
- State read/write, activations, allocation, sampling, dequantization and runtime overhead are excluded from traffic estimates; state is small but nonzero.
- Vision weights are resident but not scanned during text-only decode.
- BF16 KV formula is corroborated by the launch log: target full K/V 2 GiB each, draft 0.25 GiB each; state pools remain additional.
